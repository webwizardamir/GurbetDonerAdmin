Customer Categories

Adding a customer classification (Horeca, Supermarkt or Other) so that orders, reports and daily operations can be filtered and separated by the kind of client.

📅 18 July 2026 🎯 Admin app (app.melekhalalfood.nl) 👥 For: owner, team, client

1 The idea in one minute

Today every customer is treated the same. The client wants to know whether a customer is a restaurant or takeaway (Horeca), a Supermarkt, or something that fits neither (Other). Supermarkt clients usually order more, and later we may add stock-refill reminders for them. That reminder part is a future step, not part of this work.

Why put the label on the customer, not the product?

The client used to have categories on products and turned them off. This time the label sits on the customer. You tag each customer once, and that label then follows every order, invoice, delivery stop and analytics row that customer produces. There is no need to re-tag products.

This is a separate thing from the existing price list. A customer's price list decides what they pay. Their category decides what kind of business they are. A Horeca and a Supermarkt customer can even share the same price list.

3 Decisions locked

These are agreed and drive the build. If the client disagrees with any of them, flag it in section 6.

DecisionChoice
The categoriesFixed set of three: Horeca, Supermarkt, Other. Not owner-editable. We do not expect the list to change, and a fixed set is simpler and more reliable.
One or many per customerExactly one type per customer. Mixed or ambiguous cases go to Other.
Existing ~248 customersLeft blank (Untagged) so they surface for tagging, with no wrong guesses.
ScopeFull build, all features included. The setup, the type filters everywhere, and the daily-operations separation (routes, sold-products, day-close) all ship. It is built in a sensible order, but nothing is left out.

4 The plan

This is the full build. Everything the client asked for is included. It is done in two parts, in this order, because the setup and filters have to exist before the daily-operations screens can use them. Both parts ship.

PART 1  Setup and filters

  • The field itself: add the category to the customer, add the dropdown to the customer form, and the colored badge.
  • Customers list: filter by type plus a badge column, so the client can work through the untagged ones.
  • Orders list: filter orders by customer type, and show it on the row.
  • Analytics: slice every report by customer type (revenue, profit, top customers, and so on).
  • Exports: a "Klanttype" column on the Orders and Customers exports (Excel, CSV, PDF).

Mostly filters and a column. Once this is in, the client can tag customers and report by type.

PART 2  Daily operations

  • Sold Products: option to group by, or show only, a chosen customer type.
  • Delivery route: plan a route for one customer type, for example a Horeca-only run.
  • Day Close and daily invoices: generate the daily batch for one type only.

A bit more work, because these screens do their counting on the server, so the change reaches a little deeper. All three are included in this build.

🔭 Genuinely later, not part of this build: stock-refill reminders aimed at Supermarkt customers. Noted here only so it is not forgotten.

5 Open questions for the client and team

A few things to confirm before we build. Answers here will not change the overall shape. They just settle wording and edge cases.

  • Are three categories genuinely enough? The client mentioned some customers "fall under different categories." We plan to send those to Other. If there is a real fourth type coming, such as wholesale, catering or butcher, tell us now. It is cheap to add before we start and harder to pull back out of "Other" later.
  • Display names and language. Should the labels be Dutch in the app: Horeca / Supermarkt / Overig? Confirm the exact wording for each.
  • Badge colors. Proposed: Horeca is blue, Supermarkt is green, Other is grey. Any preference?
  • Should the category ever appear on customer-facing documents such as invoices or order confirmations? Our recommendation is no, since it is an internal classification. Please confirm.
  • Who tags, and how fast? With ~248 customers starting untagged, does the client want to bulk-tag them in one session, or tag them gradually as orders come in? This only affects how visible the "Untagged" state should be.

6 How it is built, in plain terms

A short, non-technical summary of the work, so everyone can follow what is happening under the hood. The developer notes are kept light on purpose.

The one thing everything depends on

We add a single new setting to each customer that stores their type. Because it is one clean setting with only three allowed values, every screen can read it the same simple way. There is no extra table and no complicated wiring, which keeps it easy to maintain and hard to break. Existing customers keep this setting empty until someone fills it in.

What changes on each screen

ScreenWhat we do
Customer formAdd the type dropdown, next to the price list.
Customers listAdd a type filter, a badge column, and the ability to sort by it.
Orders listAdd a type filter, and show the type on each order row.
AnalyticsAdd customer type as one more way to slice the reports, like customer and product already are.
ExportsAdd a "Klanttype" column to the Orders and Customers export files.
Sold ProductsAdd the option to group by, or show only, a chosen type.
Delivery routeAllow planning a route for one type, for example Horeca only.
Day CloseAllow generating the daily batch for one type only.

Most of these are simple filter changes. The reports, sold-products, route and day-close screens do their counting on the server, so those few need a slightly deeper change so the server understands the new type as well.

About the old product categories

The old category system that was on products is still sitting in the background, just switched off in the screens. We are leaving it alone. It labelled products, and this new feature labels customers, so they are two separate things and there is no need to touch the old one.

Extra detail for the developer
  • Storage: a nullable customer_type text column on customers with a 3-value CHECK (empty means untagged). No new table, no join. Text plus CHECK, not an enum, so adding a value later is trivial.
  • Types: add customer_type to the Customer type and the customer form data, plus one shared label and color map for the badge.
  • Watch-out on Orders: the type sits on the joined customer row, so the order filter needs an !inner embed or an id pre-resolution (like the existing name search), not a plain .eq on orders.
  • Server side: the analytics, sold-products-breakdown, route and day-close queries each need the new type added as a parameter or returned column (a migration on the relevant RPCs).
  • No backfill: existing rows stay empty on purpose, so untagged customers stand out.
