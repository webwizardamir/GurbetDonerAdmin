### 🚨 `supabase/` does not deploy on push

A push to `main` rebuilds the Vercel project. **Vercel never deploys `supabase/`.** Committing a
migration is not applying it, and committing an edge function is not deploying it. Apply migrations
with the Supabase MCP `apply_migration`; deploy functions from the **repo root**:
`npx supabase functions deploy <fn> --project-ref dvpnvulxkccurqkpqqnx --no-verify-jwt`.
`--no-verify-jwt` is **mandatory** for the cron-secret / public functions
(`plan-delivery-route`, `process-invoice-reminders`, `portal-request-code`, `sync-email-status`) —
MCP and the CLI default it to true and 401 the cron.

### 🚨 Current state of this deployment

Not yet fully live. Check these before assuming a feature works:
- **Both `pg_cron` jobs are `active = false`** (`process-invoice-reminders`, `sync-email-status`).
  They read `project_url` + `reminder_cron_secret` from **Vault, which is empty**. Do not enable

## Project Overview

B2B wholesale platform for halal food distribution: customers, batch/expiry inventory, orders,
document generation, analytics. Two roles — **Owner** (everything) and **Shop Manager**
(operational; no cost/profit/analytics/settings). Mobile-first, Dutch/EU invoicing compliance.

---

## Tech Stack

React 18 + TypeScript + Vite 6 · Tailwind v4 · Supabase (Postgres + Auth + Storage) ·
`@react-pdf/renderer` (+ jsPDF/html-to-image for the analytics page export) · React Hook Form + Zod ·
TanStack Table · Recharts · exceljs · Lucide · React Router v7 · react-i18next.

**State: React Context + hand-rolled `useState`/`useEffect` hooks (`hooks/use*.ts`). React Query is
NOT installed** — there is no caching, deduping or refetch-on-focus unless a hook implements it.

---

## Architecture Principles

- **Append-only audit log** — mutations logged with who/when/old/new.
- **Immutable order prices** — sold price + cost snapshotted on the line, never recalculated.
- **Soft deletes** — `is_active` / `deleted_at`, never hard delete.
- **RLS on every table**; role checks belong in the RPC, not only the UI.
- Stock model in production is the simple `products.stock_quantity` counter (batch/FIFO tables exist
  but are not wired into the live deduct/restore path).

## Conventions

**Files** — Components/Pages `PascalCase.tsx`, hooks `useCamelCase.ts`, utils `camelCase.ts`.
**Structure** — `src/{components/{ui,layout,<domain>},pages,hooks,services,context,types,utils,lib}`.
**DB** — tables `snake_case` plural, columns `snake_case`, FKs `{table_singular}_id`, indexes
`idx_{table}_{column}`.
**TypeScript** — interfaces for shapes, enums for fixed sets, type params and returns, `unknown` over
`any`.
**Money** — stored as integer cents; displayed `€1.234,56` (`nl-NL`, hardcoded everywhere).
**Dates** — `timestamptz` (or DATE for `order_date`); displayed `DD-MM-YYYY`.
🚨 **Copy: never an em dash (`—`) in user-visible text** — locale strings, hardcoded UI strings, PDF
and email copy, in every language. Use a comma, a colon, a full stop or ` · `. (Code comments are not
copy. The lone `—` standing in for an empty value in a table/PDF cell is a symbol, not punctuation,
and stays: a hyphen there reads as a minus sign in a price column.)

### Internationalization

- Admin: **NL** default, **EN** and **TR** secondary. Portal: **NL/EN only** (`PORTAL_LANGUAGES`).
  Locales in `src/i18n/locales/{nl,en,tr}.json`.
- **Add keys to all three files** (NL first). A missing `tr` key silently renders Dutch; a dropped
  `{{placeholder}}` renders an **empty string** into live UI. Run **`node scripts/check-locales.mjs`**
  (from `apps/admin`) after touching any locale — it diffs keys *and* placeholder sets against
  `nl.json` and exits non-zero.
- **Customer-facing documents and emails are NOT driven by app language** — they pick NL/EN from the
  customer's country (see *Documents → language*). Do not wire app language into either.

## Turkish

- `tenant.languages` (`config/tenant.ts`) lists what the admin switcher offers: `['nl','en','tr']`.
  Language names are **never translated**. The portal stays NL/EN via `PORTAL_LANGUAGES`.
- **`supportedLngs: tenant.languages` gates the DETECTOR**, not just the switcher.
  `load: 'languageOnly'` normalises `nl-NL` → `nl`.
- **Turkish is opt-in, never inferred**: `i18n/index.ts` demotes a browser-inferred `tr` back to `nl`,
  and reads `localStorage` **before `init()`** (the detector's `caches:['localStorage']` writes the
  guess back, after which an explicit choice is indistinguishable from it).
- **`tr.json` is lazily imported** and `main.tsx` awaits `i18nReady` before first render — a late
  `addResourceBundle` does **not** re-render react-i18next without `bindI18nStore`.
  `ensureLanguageLoaded()` is awaited in the switcher for the same reason; both swallow a failed
  fetch → Dutch, never a blank app.
- **Known and deliberate:** dates stay `nl-NL` in a Turkish session, and `AuditLog` titles stay Dutch.
  If dates ever change, use a `uiLocale()` helper **only** for prose dates in app chrome (dashboard
  greeting, `OrderDetail.formatDateLong`). 🚨 **Never touch `utils/format.ts`** — it feeds the
  customer PDF templates.

## UI conventions

### Row-click
Every entity list gives the **whole row** a meaningful click (mirroring `components/orders/OrdersTable.tsx`):
`onClick` on the `<tr>`/card, `cursor-pointer` + hover bg, and
**`onClick={e => e.stopPropagation()}` on every cell/control with its own action**.
Wired on Invoices, PriceLists, Users, PortalManagement, Analytics Orders/Customers.
**OverdueInvoices is intentionally excluded** (action-dense rows); report/aggregate tables have no
row-click by design.

### Modal backdrop
Canonical: **`bg-black/50 backdrop-blur-sm`** — the value in `components/ui/Modal.tsx`. Any bespoke
full-screen overlay must use the same classes. Never ship an overlay with no blur or a different dim.

### Mobile toolbar system
Every list page condenses to one row: `[primary filter] [⚙ Filters ③] [⋮] [action]`, rest in a sheet.
- **`components/ui/filterTypes.ts` — filters are declared as DATA**, which is what lets one
  declaration render as a desktop bar *and* sheet rows. `noAll?: boolean` marks a select that always
  holds a value (otherwise you get a duplicate "all" option).
- 🚨 **Dual-render rule:** `ListToolbar.tsx` splits mobile/desktop **once in JS** (`useIsMobile()`),
  never with CSS `hidden`/`md:`. Anything that portals or owns overlay state must be gated in JS —
  two mounted copies sharing one open-state produce a phantom menu at (0,0) (a hidden anchor's rect
  is 0). CSS visibility is only for portal-free markup.
- **`ToolbarAction.renderOverlay`** exists because a dialog trigger inside the ⋮ menu is destroyed by
  its own click (`DropdownMenu` returns `null` when closed). Overlays render at the toolbar root,
  always mounted; `ExportMenu` has `headless` + controlled `open` for this.
- **`SearchSelect.tsx`** — sticky search row, popover in the `DropdownMenu` portal, progressive reveal
  with "showing X of Y", supports `multiple`. Autofocus the search on **desktop only**.
- The filter sheet **live-applies** (no draft state) so its footer can show the page's real
  `totalCount`.
- `useOverlay` (scroll lock, Escape, focus trap) is shared by `Modal` and `Sheet` — a leaked ref-count
  there freezes page scroll permanently.
- 🚨 `utils/dateRange.ts` holds Amsterdam-pinned date primitives (`ymdInAms`). **Never
  `new Date().toISOString().split('T')[0]`** — between midnight and 01:00/02:00 local it returns
  *yesterday*, exactly when day-close and route planning run.

### List pages keep view state in the URL
`/customers?page=2&type=horeca` via **`hooks/useUrlListState.ts`** (Customers, Orders, Products,
Invoices, Outbox). Detail/editor back buttons use **`useBackTo(fallback)`** — a forward
`navigate('/orders')` throws the state away.

**The mirroring is one-directional — keep it that way:**
1. Parse the URL **once** on mount (`urlInit`) to seed local state + the data hook.
2. `setUrlState({...})` only from **event handlers**, or effects that skip their initial run.
   **Never write the URL from a mount-time effect** — an inbound `/orders?status=pending_payment`
   (Dashboard tile) would be stripped before the page read it.
3. Any "reset to page 1 when filters change" effect must **skip its first run** (`filtersInitRef`).
4. Default-valued keys are omitted; writes use `{ replace: true }`.

🚨 **The `?gs=` remount key is the one escape hatch.** Parsing once on mount means navigating to the
page you are *already on* changes nothing but the address bar. `Layout.tsx` wraps `<Outlet/>` in a
`<Fragment key={searchParams.get('gs')}>`, and the header search appends `gs=<n+1>` **only when the
destination pathname equals the current one** (`withRemountKey` in `SearchBar.tsx`). Nothing else may
write `gs`, or paging and typing would remount the page under the user.

### Global search (header)
`components/layout/SearchBar.tsx` + `hooks/useGlobalSearch.ts` + `services/search.ts`. Grouped
Klanten / Bestellingen / Producten, debounced 250 ms, aborted + request-id guarded, 30 s result
cache, Cmd/Ctrl+K, arrow-key navigation, recent picks in `localStorage`.
- 🚨 **Desktop and mobile branch ONCE in JS** (`useIsMobile`), like every other portal-owning
  component. The old CSS split (`hidden md:block` + a `md:hidden` overlay) bound the click-outside
  handler to the desktop wrapper only, so on a phone a tap on a result counted as "outside": the list
  unmounted on `mousedown` and the row's `onClick` never fired. Tapping a result did nothing.
- The results container carries `onMouseDown={e => e.preventDefault()}` so the input keeps focus. Let
  it blur and the mobile keyboard collapses mid-tap, the list slides up, and the finger lands on
  another row.
- 🚨 **Every result url must OPEN the entity**, never a bare list page: customer `/customers/:id`,
  order `/orders?order=<id>` (the param `Orders.tsx` reads on mount), product
  `/products?search=<sku>` (there is no product detail route). Order hits are matched by order
  number, legacy `woo_invoice_number`, app-issued document number and customer name.
- Trashed orders are excluded; archived customers rank last behind a "Gearchiveerd" pill.
- The `.or()` term goes through the same `[%"\\]` strip as `services/orders.ts` / `utils/pgSearch.ts`.

### Strong-password policy
Single source: **`utils/password.ts`** — min 12 chars + upper + lower + digit (`checkPassword`,
`passwordProblemKey` → `auth.passwordPolicy.*`), UI `components/ui/PasswordRequirements.tsx`.
Enforced at every **set-password** site (never at login) and **mirrored server-side** in the
`create-user` and `manage-portal-account` edge functions. **Change the policy = change all three.**

The whole family is spaced around the brand blue so the **invoice** keeps it: a proforma wearing the
invoice colour reads as payable when it is not. The rule that survives a photocopy: **darkest navy
band = money is due**.

🚨 **BRAND ≠ SEMANTIC — do not sweep the remaining hexes out of the templates.** These are not
branding and must stay put: the amber `verlegd` notice, the red due-date, the green in `CreditNoteTemplate` (money coming
back) and in `PaymentReminderTemplate`'s bank block (pay here), and `SoldProductsTemplate`'s
critical/low/ok badges. Same reason `index.css` refuses to remap `emerald`.

🚨 **A template cannot import `config/tenant.ts`.** PDFs never see a stylesheet, so the dashboard's
CSS-variable recolour of the `green` ramp does **not** reach them — that is exactly why
`brandPalette.ts` exists. `InvoiceTemplate` is **also bundled into the Vercel Node function**
(`api-src/render-invoice.tsx` → `api/render-invoice.mjs`), where the config's logo PNG import dies.
Templates must stay asset-free. (Before the repo split this went through a `config/tenantId.ts` shim
plus an esbuild `define`; both are gone, the constraint is not.)

🚨 **A template cannot import from `src/services/*` either — same reason, worse blast radius.**
Every service imports `services/supabase.ts`, which reads `import.meta.env.VITE_SUPABASE_URL` and
touches `window` at **module scope**. Pull one into the template graph and the bundled Lambda throws
while *loading*, so `/api/render-invoice` 500s for **every** caller at once: the 24h invoice mail
(which skips the send when the PDF is null), the monthly Betaaloverzicht, and the Klantactiviteit
attachment. There is no error surface anywhere — mail simply stops arriving. It shipped exactly
once, on 2026-08-07, via a one-word import of `groupActivityRows`.
Put anything a template needs in a **DB-free module** (`src/utils/customerActivity.ts` is the
worked example, and `services/customerActivity.ts` re-exports it so call sites are unaffected).
`scripts/build-api.mjs` now fails the build on any surviving `import.meta.env` in the bundle **and**
`import()`s the output to prove it loads in Node. Keep both guards.

**Contrast:** the brand blue is 5.6:1 on white, above AA.

### Logo sizing is height-driven — `logoMetrics.ts`

Give the `<Image>` a **height and no width**; `@react-pdf` derives width from the aspect ratio, so
any logo shape fills the slot. All nine templates use `logo: { ...docLogo }` — **never an inline
width/height**. A fixed-width box is a *wide* slot: this square 720×682 mark rendered 38×36 inside
one, with ~21pt of white on each side.
- **`height` is 44**, which is also the **ceiling** — the height of the 4-line company block beside
  it, so the header never grows.
- **`objectFit: 'contain'` must stay** — `maxWidth: 120` is a safety valve for a future ultra-wide
  upload, and `contain` is what makes that clamp letterbox instead of **stretch**.
- The branded **email** shell has the same rule — see *Email → branded shell*.

### Language — by customer COUNTRY, not app language
`resolveDocumentLang(country)` (`utils/documentLang.ts`): **NL/BE → Dutch, everyone else → English**.
`buildInvoiceData` sets `InvoiceData.lang` (stored in the snapshot) and swaps settings labels to
`EN_LABELS`/`DOC_TITLES_EN`; templates read all prose from `getDocText(data.lang)`
(`services/documentLabels.ts`). This is a **different axis** than VAT reverse-charge
(`country !== 'NL'`) — a BE customer gets a Dutch doc that still carries the reverse-charge notice.
**Do not merge the two rules.** Internal docs (SoldProducts, route, data export) stay Dutch.

### Delivery address vs invoice address
- **`utils/address.ts` → `resolveShippingAddress(customer)`** returns the shipping address **only when
  filled in AND actually different from billing**. Do **not** simplify to
  `shipping_same_as_billing === false` — several WC-imported customers have that flag false with a
  byte-identical address, and printing the same block twice reads as a bug. Postal codes compare
  space-insensitively.
- **`InvoiceData.customer.deliveryAddress?` is optional on purpose** — snapshots frozen before the
  field existed omit it and templates fall back to the single-address layout, so the portal stays
  correct.
- **Invoice / Proforma / Order confirmation** render a **dual block** (delivery left, invoice right)
  sharing the width the single box used (`addressGroup` 58% + `addressBoxHalf` 48.5%, name 9pt) — it
  costs **no extra vertical height**. Don't stack them vertically.
- **Packing slip** uses the delivery address in its "Afleveradres" box (falls back to billing).
- **Credit note + payment reminder stay billing-only** by design.

### Box (doos) dual price
When an order has any `doos` line, priced templates show **Eenheidprijs** (per single unit) +
**Doosprijs**. Gated on `hasBox`, so non-box docs are unchanged.
🚨 **Eenheidprijs is DERIVED from the actual sold box price**, never a flat catalog lookup:
`buildInvoiceData` fetches both the piece and doos defaults from `product_unit_prices` and computes
`round(soldUnitPrice × defaultPiece / defaultDoos)` (= sold box price ÷ pieces per box), so a
negotiated price scales to the piece level. Falls back to the catalog piece price only when the doos
default is missing. Analytics is unaffected — it reads the `order_items` snapshot; this value is
PDF-cosmetic.

- **Notitie column auto-hides** when no line has a note (`hasNotes`), so Omschrijving reclaims the

- Sequential numbering and price snapshots are enforced server-side; templates only render.
- New template = copy `InvoiceTemplate.tsx`, add a doc type to `brandPalette.ts`, point styles at it

## Documents

1. Sequential numbering per type (Invoice / Proforma / Credit Note) — legal requirement.
2. Required Dutch/EU compliance fields. No order locking after invoice, but all changes are logged.
3. The **Credit Nota** reflects what was actually refunded: with refund rows, `buildInvoiceData`
   rebuilds lines/totals from cumulative `order_refund_items`; a plain cancellation falls back to the
   full order.

### 🚨 Numbering is assigned server-side and atomically
`getNextDocumentNumber` calls the SECURITY DEFINER RPC `get_next_document_number_atomic(p_doc_type)`
(guarded by `is_admin_user()`), which under a `FOR UPDATE` lock on the `document_settings` singleton
returns `GREATEST(stored_counter, max_used_for_type + 1)` and stores `next + 1`. This makes a
duplicate impossible and **self-heals** counter drift (EOM resyncs, manual edits, WC imports, aborted
batches) — drift used to produce `documents_document_type_document_number_key` 409s that made Day
Close produce nothing. **Never resurrect the client-side read-increment or the unused DB
`get_next_document_number` (00018).** A new `document_type` must be added to the RPC's `CASE` and the
TS `DocumentType`, or it returns a NULL prefix.

**ORDER numbers self-heal the same way** (00110): `generate_order_number()` uses the identical shape.
Its `max_used` filters `order_number ~ '^[0-9]+$'` because the column is TEXT — a future prefixed
import must be skipped, not crash the cast. (The bare read-increment 409'd *every* order-create on
Gurbet.) Do not revert.

### 🚨 Snapshot vs live — two rendering sources
The **Orders page** rebuilds documents **live** from the current order (`DocumentGenerator` →
`buildInvoiceData`); the **Invoices page** and the **customer portal** render the frozen
`documents.snapshot`. They diverge whenever an order is edited after generation.

`refreshOrderDocumentSnapshots(orderId)` (`services/documents.ts`) re-freezes every document of an
order, **preserving the number** (`buildInvoiceData` returns `documentNumber: ''` and never allocates
one). It is parallel, best-effort (never throws) and called **fire-and-forget** after
`updateOrderWithItems` / `updateOrderNotes`. The Invoices-page download also rebuilds live and
**writes the fresh snapshot back**, so the portal heals on next open.

  blast. Send time = `send_hour` Europe/Amsterdam on a working day; a weekend rolls forward.
  **Never revert to `created_at`.**
- 🚨 **The floor counts SEND days, never calendar days.** With `working_days_only` the cron sends

  and left no trace: that is how FC-08734 and FC-08739 were never emailed on 2026-08-10. Reach is
  bounded at 5 calendar days (a Monday run stops at the previous Wednesday), and
  `!!cfg.working_days_only` must keep mirroring `dayOk` exactly — defaulting it to *true* would widen
  the window on a tenant that sends daily, and a wider window is more mail.
  **Widening this window is safe only because the dedup is exclusion-based** (`NOT IN
  (pending,failed)`): an order already handed to Resend is skipped whatever its final status. Verify
  that predicate before touching the floor again.
- Owner env: Vercel (`SUPABASE_SERVICE_ROLE_KEY`, `RENDER_SECRET`; URL reuses `VITE_SUPABASE_URL`),
  edge fn (`RENDER_ENDPOINT_URL`, `RENDER_SECRET`). Gurbet has neither, so renderer-dependent steps

## Maandelijks Betaaloverzicht (statement of account)

One landscape PDF per customer listing its **overdue** billed orders plus one total, emailed on the
**first working day of the month**. Replaces getting six separate dunning emails and never seeing one
number.

- **Overdue-gated on both axes** (00107): a customer with nothing overdue gets **no** statement, and
  the statement lists **only** overdue invoices — chasing money that isn't owed yet undermines the
  chase. Overdue is `invoice_due_date < CURRENT_DATE` (due *today* is not late).
- **`get_payment_overview_orders(p_customer_id, p_overdue_only DEFAULT false)`** — the **document
  builders pass TRUE**, the **admin tab passes FALSE** (owner keeps the full picture behind a
  "4 facturen · 3 verlopen" split). One definition, so a preview can never disagree with what is
  mailed. Qualifying: `deleted_at IS NULL`, `status NOT IN (completed,cancelled,refunded,draft)`, an
  invoice number exists (invoice `documents` row or `woo_invoice_number`), `total − refund_amount > 0`.
- **`get_payment_overview_customers(period)`** is the tab list + the cron candidate query and returns
  this month's send state in one round-trip, plus `overdue_cents`.
- **The tab shows who will actually be mailed** — one `dispatchOf()` helper mirrors Step 7's gates in
  order and drives the stat tile, the "Verzending op de 1e" filter and a per-row badge
  (*Wordt verstuurd / Binnen termijn / Geen e-mailadres / Afgemeld*). "Has overdue" is **not** the same
  set — most customers have no email address.
- **Storage: `payment_overviews`, NOT `documents`** — a statement has no sequential legal number, so a
  `documents` row would pollute the register, force a CASE branch into
  `get_next_document_number_atomic` and burn an invoice number. Unique on `(customer_id, period)`,
  upserted, linked to the mail log via `document_send_id`.
- **PDF `PaymentOverviewTemplate.tsx`, A4 LANDSCAPE** (six columns of dates and amounts need ≈786pt).
  Header band and footer are `fixed` so a 40-invoice statement keeps its column headers. Wording:
  **"Totaal te betalen"** (not "Totaal openstaand" — it is not the whole balance), no Status column
  (every row would read "Verlopen").

🚨 **`payment_overview` is its own `document_type` — never reuse `payment_reminder`.**
`get_overdue_invoices` and the edge fn's `max_count` dedup COUNT `payment_reminder` sends to place an
invoice on the dunning ladder; logging a statement as one silently consumes escalation steps. The
value is used **only** on `document_sends` and is deliberately absent from the TS `DocumentType` union
and `getDocumentTemplate`'s switch.

🚨 **The RPC guard is `IF auth.uid() IS NOT NULL AND NOT is_owner()`** — a plain `IF NOT is_owner()`
locks out the **cron** (service_role, NULL `auth.uid()`). Since only owners and the service role get
in, there is deliberately **no** `hidden_from_managers` predicate inside; that is also why the whole
tab is owner-only (gating the list but not the PDF would print a total that disagrees with the screen).

**Two send paths, one snapshot shape.** Manual (`/overdue?tab=overview` → Nu versturen) renders
client-side and calls `send-document-email` with `order_id`/`document_id` **NULL** and
`payment_overview_id` instead, writing `document_send_id` back **only on success**. Automatic is
**Step 7** of `process-invoice-reminders` (not its own cron — that would need new Vault entries on both
tenants), gated on `monthly_overview_enabled` (its own opt-in, **not** under `auto_send_enabled`) +
renderer configured + the hour/working-day window + `isFirstWorkingDayOfMonth` (a weekend 1st rolls to
Monday; enabling mid-month never backfills). Order: **upsert snapshot → render → insert pending send →
send → link**. Dedup is `status NOT IN ('pending','failed')`.
`buildOverviewSnapshot` (edge fn) and `buildPaymentOverviewData` (`services/paymentOverview.ts`) write
the same column — **keep them in sync**.

🚨 **`order_is_hidden(NULL)` is FALSE — the Outbox hole (00104).** The `document_sends` policy is
`is_owner() OR NOT order_is_hidden(order_id)`, and a statement's `order_id` is NULL by design, so a
Shop Manager could read a body containing a total that *includes* hidden orders. 00104 replaced the
whole policy with an explicit `document_type <> 'payment_overview'` term. **Any future
`document_sends` row with a NULL `order_id` inherits this hole — gate it by type the same way.**

## Key Business Rules

### Stock
1. Deducted when an order is **created** (the `order_items` insert trigger), not on delivery.
2. Cancelled orders restore the **not-yet-refunded** units (`handle_order_status_change`).
3. Refunds restore per refunded unit inside `create_order_refund` — **never** re-add a `refunded`
   branch to the status trigger, it double-restores.
4. Trash/restore/purge reuse the `cancelled` transition rather than new stock code.

### Pricing
1. Products support kg / piece / zak / doos with independent pricing; customer-specific prices can
   override any unit.
2. **Resolution chain:** `customer_prices` → `price_list_items` (active only) → `product_unit_prices`
   → `base_price`. Cost chain (`resolveLineCostCents`): list cost → unit cost → product cost → 0.
3. **Sold price and cost are snapshotted immutably on the line.** Price changes never touch history.
4. **Remembered customer prices:** editing a line price in `OrderForm` auto-saves it to
   `customer_prices` **on submit** — only when it differs from the base/list tier, deduped per
   product+unit, skipped for imported (WC) orders. Shows an amber "Onthouden prijs" badge with a
   forget × (`clearCustomerPrice`, handles unit-less `*` rows). No global promotion; rows never expire.
   - 🚨 **Keyed per unit_type** — a price remembered for `piece` does NOT apply to a `doos` line. This
     is by design and is the usual explanation for "the remembered price didn't apply".
   - Applying it depends on the async `customerPrices` context; the `loadingPrices` flag gates the
     add-product button, because in edit mode the reprice effect won't correct it afterwards
     (`repriceArmedRef` is false for loaded orders).
5. **A product may appear on an order any number of times** as separate coexisting lines — same or
   different unit (e.g. separate storages at one delivery address). Each line is its own `order_items`
   row with its own qty/unit/price/discount/note. No DB uniqueness on
   `(order_id, product_id, unit_type)`; stock/invoice/analytics all work per row.
   🚨 **Add behaviour splits by entry point** (`OrderForm.addProduct(product, merge)`):
   - **Picker add (`merge=false`)** → always a **new line**, even if the product+unit exists.
   - **Barcode scanner (`merge=true`)** → **increments the latest matching line** (scan ×5 = qty 5).
   - **Do not re-introduce a merge/dedup by `product_id + unit_type`.** Three merge points were removed
     (picker add, the reprice effect — now 1:1, and `changeUnitType` — now just switches the unit).
     Re-adding any collapses the customer's separate lines.
   - The scanner is **not in daily use yet**; if scans start duplicating lines, check the `merge` flag
     through `addProduct` → `addProductWithUnitType` → `handleUnitTypeSelect`, not the removed logic.
   - Accepted limitation: with one product+unit split across lines at *different* edited prices, only
     the first is remembered for next time.

### Catch weight — counted in pieces, priced per kilo (00117)
Döner spits, packs and trays are counted as pieces but sold by the kilo. One line is three factors:
`stuk (kg) × aantal × prijs per kg` (7 × 35 × €4,70 = €1.151,50).

🚨 **`quantity` STAYS THE KILOS. `piece_count` / `piece_weight_kg` are DESCRIPTIVE and never a second
source of truth for money.** That is the whole reason the feature costs no SQL anywhere else:
`computeOrderTotals`, the stock triggers (they subtract `NEW.quantity`, i.e. kilos), `create_order_refund`'s
server-side recompute, every analytics RPC, the 00109 net-revenue rules and the price chain are all
untouched, and `customer_prices` keeps holding the **€/kg the customer actually negotiated**.
**Never "simplify" this to `quantity = 35` + a derived per-piece `unit_price`** — that stores a number
nobody typed and poisons remembered prices and price lists.

- **The weight lives on the LINE**, snapshotted immutably beside `unit_price`/`cost_cents`, because a
  spit is a *range* and moves per delivery. `products.default_piece_weight_kg` is a **prefill only**;
  editing it must never reach an order that already exists.
- Three CHECKs, all load-bearing: both columns or neither, both `> 0`, and `unit_type = 'kg'` (the
  derived number *is* the kilos, so there is nothing for a weight on a `doos` line to multiply into).
  `changeUnitType` and the reprice fallback clear the pair on the way out of kg.
- **Filling "Stuk (kg)" is the switch** — no mode toggle. The Aantal field then edits `pieceCount` and
  `quantity` follows; clearing the weight **keeps the kilos**, never the piece count, because the kilos
  are what the line is priced on. `+/-` and the barcode scanner step **pieces**, not kilos.
- Rounded **once**, in `catchWeightQuantity` (`utils/catchWeight.ts`), to 3 decimals — matching
  `order_items.quantity` NUMERIC(10,3) and the form's own free-typed rounding. Round at display time
  only and an invoice shows 244,999 kg beside a total priced on 245.
- **`utils/catchWeight.ts` is imported by the PDF templates, so it must stay DB-free and asset-free**
  (it may import `utils/format.ts` and nothing else). Same rule as everything else in a template graph.
- `InvoiceData.items[].pieceCount/pieceWeightKg` are **optional on purpose**, like
  `customer.deliveryAddress` — snapshots frozen before 00117 omit them and every template falls back
  to the plain quantity, so the portal keeps rendering old invoices.
- Surfaces: order form, order detail, refund modal (as **context**, not a second input), the five
  customer documents (see *Catch weight on the documents* below), portal order detail, the route stop +
  loading lists and the driver's route PDF.
- **Sold Products is deliberately untouched**: it aggregates per product+unit across customers, and
  summing pieces whose weights differ per line is meaningless. Kilos are the right unit for that report.

### Catch weight on the documents — the customer's three columns

The customer models a line as **three factors**, not two, and asked for his documents to read that way:
`stuk (kg) × aantal × prijs per kg` (his `voorbeeld (3).xlsx`, gitignored at the repo root). The five
customer documents print exactly that:

`# | Omschrijving | [Notitie] | Stuk (kg) | Aantal | Eenheidprijs [| Doosprijs] | Excl. BTW | Incl. BTW`

- 🚨 **On a catch-weight line `Aantal` is the PIECE COUNT (35), not the kilos.** The kilos are absent
  from the row by design: they are the product of the three printed factors, and a fourth number
  invites the reader to check the wrong pair. `quantity` is of course still the kilos in the data and
  still what `priceExclVat` is computed from — nothing about money moved.
- 🚨 **The row states its unit exactly ONCE.** Ordinary line: in `Aantal` ("245 kg", "10 doos").
  Catch-weight line: in the price, via **`withCatchWeightUnit`** → "€ 4,70 / kg". Drop that suffix and
  a bare 4,70 beside "35" reads as the price of one spit (35 × 4,70 = 164,50, while the line says
  1.151,50). His sheet only escapes this because of a loose "kg" parked in an unlabelled column.
- The three cell rules live in **`utils/catchWeight.ts`** (`formatPieceWeight`,
  `formatPieceCountCell`, `withCatchWeightUnit`) so the five templates cannot drift. `Stuk (kg)` is
  **permanently mounted**, an em-dash on every ordinary line, so a mixed order does not shuffle its
  columns. `formatPieceBreakdown` (the old "35 x 7 kg" sub-line) survives for the **route PDF**, the
  **portal** and `OrderItemsList`, which are not laid out in columns.
- **The per-line BTW column was dropped** to match his sheet and to buy the width. This stays
  compliant: the totals block already breaks VAT out per rate, which is what the law asks for. Putting
  it back means re-widening `colDesc`.
- **His sheet's `INCL. BTW` is unrounded** (1255,135). The app rounds VAT per line and prints 1.255,14.
  Keep the rounding.
- **Credit note: same columns, cells usually empty.** Its lines are rebuilt from `order_refund_items`,
  which carry no piece fields (a partial refund need not land on a whole spit), so `Stuk (kg)` is a
  dash and `Aantal` shows kilos — the old "kilos only" behaviour, now expressed as a blank column
  rather than a missing one. They fill in only on the full-order fallback (a plain cancellation),
  where the credit note does mirror the invoice line for line. **Do not gate the column away**: parity
  with the invoice is the point.
- **Packing slip** shows pieces for the same reason the route list does: that is what the person
  loading the van counts. Its "Totaal per eenheid" footer still sums kilos.

### VAT (BTW) — reverse charge
1. NL customer → the product's `tax_rate` (9% food / 21% non-food / 0%).
2. Non-NL customer (rule is `country !== 'NL'`) → **0% BTW forced on every line** at create/edit, and
   the customer's VAT number must appear on the invoice.
3. Invoice / Proforma / Credit Note carry the "BTW verlegd" notice for non-NL.
4. **Imported (WC) orders are frozen** — `isImportedOrder()` (= `woo_invoice_number` or
   `woo_invoice_date` set) bypasses the rule on edit; the original BTW is preserved verbatim.
5. Helpers in `src/utils/vat.ts`; enforced **client-side in `OrderForm`** (the service layer trusts the
   `tax_rate` it receives).
6. Out of scope: VIES validation, OSS/B2C distance sales, Opgaaf ICP.

### Per-order shipping fee ("Verzendkosten")
Replaces the old "Transport product" workaround, which polluted the goods subtotal and counted as
profit.
- Stored in the existing **`orders.delivery_fee`** (ex-BTW cents); flat `€` input in the order-form
  totals strip; row hidden when empty; shown on invoice/proforma/order-confirmation totals, excluded
  from credit notes.
- **BTW:** entered ex-BTW, follows the order's dominant goods rate (0% for reverse-charge). One shared
  helper **`resolveShippingVat`** (`utils/discount.ts`) is used at save, in the form preview and in the
  document, so amounts never drift (VAT rounded once). Imported WC orders keep their frozen total.
- 🚨 **Profit-safe invariant:** shipping stays OUT of `subtotal`/`discount`/`tax` and only folds into
  `orders.total`. Profit reads `subtotal` + `cost_cents`, so shipping is never revenue or profit.
  **Do not add it to subtotal.** `recalculateOrderTotals` must keep re-adding it (+VAT) to `total`
  while the goods figures stay goods-only.
- 00078: the "fully refunded" test compares against the **goods total** (`Σ order_items.total`), not
  `orders.total`, or a shipping order can never reach `refunded`.

### Refunds
Issued from the order detail panel (→ `RefundModal`), deliberately separate from the status buttons.
1. **`create_order_refund`** does everything atomically: `is_admin_user()` guard (owner **and** shop
   manager), recomputes each line amount **server-side** from the immutable snapshot
   (`total`/`tax_amount`, already discount-inclusive), inserts `order_refunds` (gross) +
   `order_refund_items` (ex-VAT + tax), increments `orders.refund_amount`, restores stock for
   `track_stock` products. The client sends only `{ order_item_id, quantity }[]` and can never set the
   amount.
2. A **full** refund (cumulative ≥ total) flips status to `refunded`; a **partial** keeps the status
   and shows a "Gedeeltelijk terugbetaald" badge. There is no partial status in the enum by design.
3. Guards: per line (≤ original − already refunded), per order (cumulative ≤ total); cancelled orders
   can't be refunded.
4. Analytics: a fully-refunded order is excluded from the `sold` set (and its items not subtracted
   again); partials stay in `sold` with the refunded portion subtracted. This is why full refunds flip
   status rather than staying `completed`.

### Order notes (editable in any status)
Three fields: per-line `order_items.notes` (**the only one that prints**, in the document Notitie
column), plus order-level `orders.delivery_notes` and `internal_notes` (panel only).
1. Editable in **every** status from the detail panel ("Notities bewerken" → `OrderNotesModal`) and the
   Orders-table edit icon.
2. **`updateOrderNotes`** issues plain UPDATEs, so the stock triggers (which fire on `order_items`
   INSERT/DELETE) never run. This is the **only** safe way to touch a cancelled/refunded order.
3. 🚨 Orders-table edit routing: `cancelled`/`refunded` → `OrderNotesModal`; everything else (incl.
   `completed`) → the full `OrderForm`. **Never route cancelled/refunded to the full editor** — its
   delete-and-reinsert of `order_items` re-fires the stock triggers and corrupts restored stock.
4. Delete stays restricted to `draft`/`pending_payment`/`on_hold` (audit safety), and it **trashes**.

### Order trash (soft delete)
1. `orders.deleted_at` + `orders.pre_trash_status`. The Orders page filters `deleted_at IS NULL`; the
   **Prullenbak** toggle shows the rest and renders `pre_trash_status` as the badge.
2. RPCs (all SECURITY DEFINER + `is_admin_user()` + the hidden-order predicate):
   `trash_order` (deletable set only; saves `pre_trash_status`, sets `cancelled` → trigger **restores
   stock** — and `deleted_at`), `restore_order` (status back → **re-deducts**), `purge_order` /
   `empty_order_trash` (set status back → re-deduct, **then** DELETE so the cascade restores; net
   correct, no double-restore).
3. **Why:** a trashed order carries `status='cancelled'`, so every analytics RPC already excludes it —
   no analytics sweep needed. Only the status-COUNT RPCs and the portal RLS needed explicit
   `deleted_at IS NULL`.
4. 🚨 Do not break: `purge` must keep re-deduct-then-delete, and the portal RLS + portal service
   queries must keep `deleted_at IS NULL` or trashed orders leak to the customer.

## Orders — status, lifecycle, sorting

### The pill IS the picker
`components/orders/OrderStatusPicker.tsx` — the coloured status pill in `OrderDetail` is the dropdown
trigger. Styles come from `constants/orderStatus.ts` (`statusStyle()`).
- 🚨 **Compare against `currentKey`, not `current`** — `pending` and `pending_payment` render
  identically, so comparing raw values wrote a pointless transition with no confirmation.
- **Refunded is terminal and trashed is read-only** — both render a plain `StatusBadge`. A trashed
  order is `cancelled + deleted_at` with its real status in `pre_trash_status`; editing its status
  re-deducted stock for an order in the bin *and* was silently reverted by `restore_order`.
- **Cancelled → Concept is allowed** (safest revive: no invoice, out of analytics).
  Completed/refunded → Concept is not. Reviving a cancelled order re-deducts stock and confirms first.

### `pending` was merged into `pending_payment` (00111)
One waiting status. They were always the same state under two names, but `pending` was the column
DEFAULT while the UI only offered the canonical one. 00111 moved the default, backfilled `status`
**and `pre_trash_status`** (miss the second and restoring from the bin writes the legacy value back).
The enum label still exists — Postgres can't DROP one without recreating the type — it is just
unreachable.

🚨 **The alias machinery STAYS — it is not dead code.** `STATUS_ALIAS` / `expandStatusFilter` /
`canonicalStatus` (`constants/orderStatus.ts`) guard every status filter and read, because the label
remains writable and because `audit_logs` rows and frozen `documents.snapshot` blobs are immutable
history containing the old string.
- **Filtering** — `fetchOrders` *and* `fetchOrderCount` expand (both, or list and pagination
  disagree), and so does **`statusArg()`** (`services/analyticsHelpers.ts`), the choke point every
  analytics RPC goes through. Missing it reported 4 of 248 orders / €1.384 of €111.919.
- **Reading a status back** needs `canonicalStatus` — `get_orders_by_status` groups the raw column, so
  the Overview pie drew two identical slices until `getOrdersByStatus` merged them.
- 🚨 **Never hand-write a second status→label or status→colour map.** Derive from `STATUS_STYLES`
  (`statusStyle()` / `orderStatusLabelNl()`); local copies keep omitting a value, which then renders
  grey with its raw English enum name.

### Concept (draft) orders
Opt-in `draft` status to park an unfinalised order (checkbox in `OrderForm`, status action in
`OrderDetail`). Live default is `pending_payment`.
1. **No invoice/number** — `ensureOrderInvoice` is skipped while saving a draft; finalising issues it.
2. **No automatic email** — no invoice doc, and Step 4 dunning excludes `draft` explicitly.
3. **Excluded from analytics revenue/profit** — 00089 patched 20 RPCs via a `DO` block that
   string-replaces the sold-set predicate in each live `pg_get_functiondef`. **Kept** in
   `get_today_stats` operational buckets, the status-distribution RPCs and `get_order_stats_by_status`.
   🚨 Do not hand-rewrite those functions from old migrations — the DO-block preserves live 00070
   owner-gating.
4. **Invisible in the portal** (00094) — `status <> 'draft'` on all four `get_portal_*` RPCs. The
   documents filter matters as much as the orders one: a draft **can** carry an issued invoice
   (invoiced first, set back to Concept after).
5. Drafts still **reserve stock** (deduct is on insert, status-agnostic).
6. `CreateOrderData.status?` is threaded through create/update **only when it must change**, never
   clobbering an existing completed/cancelled status.

**Finalising re-stamps `order_date` (00098) and stamps `activated_at` (00099).** A draft is a
scratchpad; keeping its start date booked revenue into a reported period, planned the wrong day's
route, and fell outside the 24h send window (so the invoice email never went at all) with an already-past
due date.
- Implemented **inside `set_invoice_due_and_paid`**, not as its own trigger: that function already
  recomputes `invoice_due_date` when `order_date` changes, and **BEFORE triggers fire in alphabetical
  name order**, so a separate trigger would depend on a naming coincidence.
- Two guards on the **date** bump, both load-bearing:
  `NEW.order_date IS NOT DISTINCT FROM OLD.order_date` (respect a date typed while unticking Concept)
  and `< today` (a future date is a planned delivery, never pulled back).
  `draft → cancelled/refunded` is excluded. `OrderForm` mirrors the rule into the visible field on
  untick.
- 🚨 **`activated_at` is set on EVERY finalisation — its transition test is split from those two
  guards.** Do not fold it back under them: a draft opened 08:00 and finalised 17:00 the same day
  already has `order_date = today`, skips the date branch, and would sort below the whole morning.
  `created_at` can't answer this (for a draft it means "scratchpad opened", and it must keep meaning
  that); for an order that was never a draft `activated_at = created_at` and never moves.
- Any backfill on `orders` must **suppress `orders_updated_at`** (BEFORE UPDATE FOR EACH ROW — it
  would stamp `updated_at = now()` on every order and destroy the edit history) **and `audit_orders`**.

**A Concept is PINNED to the top while it is still a draft (00100)** — it needs a human to come back to
it (no invoice, no email, out of analytics, **stock already reserved**), and it used to drift off page 1.
- **`orders.is_draft`** is `GENERATED ALWAYS AS ((status = 'draft') IS TRUE) STORED` with
  `idx_orders_list_sort_draft (is_draft DESC, order_date DESC, activated_at DESC)`. Generated because
  **PostgREST can only order by a column, not an expression**, and so it can never drift from `status`.
  The `IS TRUE` wrapper matters — `status` is nullable and a NULL sorts first under `DESC`.
- **Keyed on `status`, never `pre_trash_status`** — a trashed draft belongs in the bin, not pinned.
- It must be **both** server-side (the list pages 50 at a time, so a browser-only hoist strands a draft
  on page 3) **and** client-side in `Orders.tsx`, whose `useTableSort` would otherwise shuffle them
  back down. That partition is applied to **every** sort column. `OrdersTable` has no client sort.

### List sorting
`fetchOrders` orders by **`order_date DESC, created_at/activated_at DESC`** — `created_at` is only a
stable-pagination tiebreaker. Sorting by `created_at` sank future-dated orders into the wrong page.

### Bulk status updates are constrained server-side
Selection survives paging, so a stored selected row is a **snapshot**. Bulk eligibility is re-derived
from the live list (`Orders.tsx`), **and** `bulkUpdateOrderStatus` constrains the UPDATE to rows still
in a legal source status (`legalFrom`). Without both, ticking a `pending_payment` order, cancelling it
from the detail panel, then bulk-completing wrote `cancelled → completed` and **re-deducted its stock**
silently.

### The payment method belongs to `completed` — and is corrected there (00118)
`orders.payment_method` used to have exactly one writer (the `→ completed` transition), which cannot
be re-run on a completed order — so cash could never be corrected to bank. The payment badge in
`OrderDetail` is the picker (`PaymentMethodModal` `mode="edit"`), writing through
**`updateOrderPaymentMethod`**, deliberately separate from `updateOrderStatus`: it fires neither the
stock trigger nor a status transition. **Do not "fix" this by relaxing the guard in
`updateOrderStatus`** — and note the old workaround (bounce to pending, complete again) silently loses
`invoice_paid_at`.

🚨 **Leaving `completed` CLEARS the method** (`set_invoice_due_and_paid`, 00118) — the same rule
that has always nulled `invoice_paid_at`. Without it the badge survived the status change, so an
order read "Wacht op betaling · Bank", and `get_revenue_by_payment_method` (which filters
`payment_method IS NOT NULL` and includes `pending_payment`) booked an unpaid order as cash or bank
revenue. It lives in the trigger, not in `updateOrderStatus`, so the detail picker, the order form's
Concept tick and any future writer are covered at once. Two guards:
- `NEW.payment_method IS NOT DISTINCT FROM OLD.payment_method` — an explicit method sent in the same
  statement wins (mirrors the `order_date` guard above it in the same function).
- **`refunded` is excluded**: the money really arrived and has to travel back the same way. Refunded is
  terminal, so that value can never go stale again, and a *partial* refund keeps the order `completed`
  and never reaches this branch. Cancelling a completed order does clear it.
- The trash path is unaffected: `trash_order` refuses anything but draft/pending/on_hold/cancelled, so
  `OLD.status = 'completed'` never happens there.

**The badge follows the same rule in the UI.** `OrderDetail` renders it as the picker only while the
order is `completed`, read-only on refunded/trashed, and **not at all otherwise** — offering it on an
order that is still waiting for payment just recreates the same misleading pair one tap later. The
list pages need no gate: `PaymentBadge` renders null for a null method.

## 🚨 Money conventions — read before touching any revenue or profit figure

### Revenue is NET OF DISCOUNT (00109)
`orders.subtotal` is persisted from `computeOrderTotals().subtotal`, which sums
`unit_price × quantity` **before** line and order discounts. Analytics used it as the revenue base, so
profit was overstated by exactly the discount (one order: +€12,50 reported instead of a €62,50 loss).

| Output | Base |
|---|---|
| labelled **gross** (`grossRevenue`), or a column shown **beside its own discount column** | `o.subtotal` — it IS the gross figure |
| labelled **net**, or feeding **profit / margin / average order value** | subtract the discount |

Two equivalent net expressions (`computeOrderTotals` distributes the order discount proportionally
into each line's `finalBase`):
- **order level** → `o.subtotal - COALESCE(o.discount, 0)`
- **line level** → `oi.total - oi.tax_amount` — **never** `oi.unit_price * oi.quantity`
  (pre-discount) and never bare `oi.total` (includes BTW)

**Do NOT "fix" `orders.subtotal` itself** — it is correct as a gross figure and the invoice + portal
breakdowns (Subtotaal / Korting / BTW / Totaal) depend on it. `get_portal_order(s)` emit `subtotal`
beside `discount` and are deliberately untouched.

**`get_order_performance` is the exception to watch:** its `subtotal` column stays **gross** (returned
beside `discount_amount`/`tax_amount`/`total`, an invoice-style breakdown); only its `profit` and
`profit_margin` moved. A blanket replace there corrupts the display column.

### Profit base is ALWAYS ex-VAT
`order_items.total` and `orders.total` **include BTW**; `cost_cents` is ex-VAT.
- **per line** → `line_total − tax_amount` (never `line_total`)
- **order level** → the net subtotal above
- `computeOrderProfit` (`utils/orderProfit.ts`) is the single client definition and uses
  `Σ(line.total − line.tax_amount)` so the order figure equals the sum of the per-line badges above it;
  it falls back to `order.subtotal` only when given lines without snapshot fields.
- `profitClass` (`utils/format.ts`): positive emerald, negative red.
- A 0% BTW order looks correct either way — that is what masked the original bug.

### Rollback — `public.rpc_backup_pre_00109`
All 16 live function bodies were captured on **both** projects before the edit:
```sql
SELECT def FROM public.rpc_backup_pre_00109 WHERE proname = 'get_financial_summary';
```
REVOKEd from PUBLIC/anon/authenticated. **Do not drop it** — it is the only record of the pre-00109
definitions and Supabase daily backups age out.

**How to apply the next one:** 14 of the 16 were edited by a **targeted replace over each project's own
live body** (the 00089 precedent), preserving local text and predicates; only two were hand-written.
**Every replace asserts** — a missing target `RAISE`s, so a silent miss on money is impossible. Copy
that shape rather than hand-authoring a replacement body: the live body is the source of truth, and a
paste silently discards whatever local predicates it had picked up.

### Known, NOT fixed
- **`get_monthly_comparison` returns `profit` with no `is_owner()` gate** on either project (powers
  *Analytics → Financieel → Maandelijks overzicht*). The **page** is properly gated (`<OwnerRoute>`),
  so no screen a manager can open shows it, but the RPC is callable with their token. **Consciously
  accepted by the owner (2026-08-02)** as a direct-API gap. Fix = wrap `profit` only, per-project via
  an asserted replace (this is one of the two functions whose bodies diverge between databases).
- 🚨 **`orders.subtotal/discount/tax/total` are `numeric` in this database**, not `integer`.
  This breaks any RPC declaring `RETURNS TABLE(… total integer …)` — plpgsql will not coerce NUMERIC
  into an INTEGER OUT column, so PostgREST returns a **400** (it killed `/overdue` until 00110).
  **Cast in the body (`o.total::INTEGER`), never widen the signature to `numeric`** — PostgREST
  serialises numeric as a JSON *string*, which breaks the client types. The JSON therefore also
  carries decimals (`"2583618.00"`); the app's `Number()` absorbs it, but a `::bigint` cast in a
  verification query will not.

### Granular analytics filters
Slice every tab by **customer / product / payment method / unit type / customer type** via

## Security

### 🚨 SECURITY DEFINER RPCs
- Every one needs an `is_admin_user()` (or narrower) guard **and** column gating with `is_owner()` for
  cost/profit/margin.
- **Recreating one re-grants EXECUTE to `anon`** via Supabase default privileges.
  `REVOKE … FROM PUBLIC` is **not enough** — you must `REVOKE … FROM PUBLIC, anon`, and assert with
  `has_function_privilege('anon', …)`. Missing this re-leaks COGS.

### Hidden orders — `orders.hidden_from_managers` (00095–00097)
Owner-only flag (checkbox in `OrderForm` beside Concept) that hides an order **everywhere** from a
Shop Manager. The owner gets an `EyeOff` badge and a tri-state **Verborgen** filter.

**Enforced in RLS, not the UI.** Canonical predicate, written verbatim everywhere so it is greppable:
```sql
(NOT hidden_from_managers OR (SELECT is_owner()))
```
The `(SELECT …)` wrapper makes it an InitPlan evaluated once per statement, not per row.

🚨 **The child-table trap.** A child table (`order_items`, `documents`, `document_sends`,
`order_refunds`, `order_refund_items`) can **NOT** gate itself with
`NOT EXISTS (SELECT 1 FROM orders o WHERE o.id = … AND o.hidden_from_managers)` — **that inner SELECT
is itself subject to `orders` RLS.** A manager who cannot see the order makes the subquery return
nothing, `NOT EXISTS` is TRUE, and the child row is visible: the gate reads as correct and does the
opposite. Use the SECURITY DEFINER helpers `order_is_hidden(order_id)` / `refund_is_hidden(refund_id)`:
`(SELECT is_owner()) OR NOT order_is_hidden(<fk>)` (owner first, so it short-circuits).
**Any new table hanging off `orders` needs the same treatment — never hand-roll a NOT EXISTS.**

Other invariants:
- **Replace the entire policy set per table, never patch by name.** Policies are OR'd, and this
  database carried two overlapping permissive SELECT policies that would have defeated the feature on
  their own.
- The predicate goes on INSERT `WITH CHECK`, UPDATE `USING` **and** `WITH CHECK`, and DELETE `USING` —
  that is what stops a manager setting or clearing the flag.
- 15 SECURITY DEFINER RPCs carry the predicate explicitly (they bypass RLS), as do
  `trash_order`/`restore_order`/`purge_order`/`empty_order_trash` (00096 — `is_admin_user()` alone let
  a manager purge an order they could not see) and `invoice_reminders` / `invoice_reminder_state`.
- **Do NOT touch `get_portal_*`** — the customer must still see their own order.
- **Known and accepted:** order and invoice numbers come from global sequences, so a hidden order burns
  a number and its existence is inferable from the gap. Stock still moves. The flag hides amounts and
  content, not existence-by-arithmetic.
- Verification that actually proves it: impersonate a real `shop_manager` in a rolled-back transaction
  and assert the owner's period total exceeds the manager's by **exactly** the hidden order's
  contribution — that shows the gate landed everywhere and nowhere twice.

### Owner-only export columns
`utils/export.ts` holds `OWNER_ONLY_EXPORT_KEYS` + `withoutOwnerOnlyColumns(cols)`; every `ExportMenu`
call site passes its columns through it for non-owners.
- Covers cost/profit/margin **and `total_revenue`** (a customer's lifetime revenue).
- 🚨 Matching is **exact**, so `cost_cents` does not cover `cost_kg`; all four unit-cost keys are listed
  plus a `startsWith('cost_'|'margin_')` guard so a future column is owner-only by default.
  `withUnitPriceColumns` also omits cost fields from the row object for non-owners — **strip the data,
  not just the column.**
- **Deliberately NOT covered:** the Orders export's `subtotal`/`total`. A manager processes orders and
  needs each order's amount; what is owner-only is the aggregated picture of what a *customer* is worth.
- **An exported file is durable and forwardable**, so hiding a column in a table without adding its key
  here is theatre. Add both together. Customer revenue aggregates are gated in the UI for the same
  reason (each one alone reconstructs the others).

### 🚨 Never `await` a Supabase call inside `onAuthStateChange`
Supabase emits auth events from **inside its auth lock** and awaits every subscriber before releasing
it. Calling back into `refreshSession()` / `getSession()` / `getUser()` — or **any** `.from()`/`.rpc()`
query, which fetches the token via `getSession()` — makes the lock wait on itself. It is never
released, and since supabase-js takes it on every PostgREST request, **every query in the app hangs
forever, in every tab on the origin**, until a hard reload. (The "stuck on the loading spinner" bug.)

Rules for `context/AuthContext.tsx` + `context/PortalAuthContext.tsx`:
- The callback is **synchronous** and only calls `setState`; defer async follow-up with
  `setTimeout(fn, 0)`.
- **`SIGNED_OUT` means signed out** — do not "recover" it with a refresh; auth-js has already wiped the
  refresh token.
- Do **not** hand-roll a session refresh on `visibilitychange` — auth-js already does it
  (`_onVisibilityChanged` → `_recoverAndRefresh`); a second one races it and the loser presents a
  just-rotated token → 400 → `SIGNED_OUT` → the deadlock. The remaining listener in `AuthContext` is
  inactivity-logout only and makes no network call.
- The 10s watchdog around init is a safety net, not the fix.

### CSP: no `'unsafe-inline'`
`apps/admin/vercel.json` sets `script-src 'self' 'wasm-unsafe-eval' blob: 'sha256-…'`. The one hash is
`index.html`'s **pre-paint theme bootstrap**, which must be inline (external `src` = a render-blocking
request; a module script is deferred — both reintroduce the dark-mode flash).
**Never "fix" a CSP block by adding `'unsafe-inline'`.** Edit the script and `npm run build` fails with
the new hash to paste (`scripts/check-csp.mjs` hashes every inline script in `dist/`). Note
`vercel.json` header entries accept only `key`/`value` — an extra `_comment` fails Vercel's schema and
breaks the deploy.

🚨 **The committed hash is the LF hash, and a Windows build prints a DIFFERENT one.** Vercel builds on
Linux; with `core.autocrlf=true` the local working copy is CRLF, so `check-csp.mjs` fails and prints a
hash that **looks exactly like the fix and is wrong for production** — paste it and the theme script is
CSP-blocked, bringing back the dark-mode flash it exists to prevent. Verified 2026-08-26: the same
byte-identical file hashes `+PnfBDXwl4O4Ui0XmVd5/jBkZnvMQrPVnYB48BBaJcI=` (LF, correct) and
`6+Q2omgsuL/m0jSDktKHSN59wJsY+1rX4pBuwjrKJ2E=` (CRLF, local-only). `.gitattributes` pins
`apps/admin/index.html` to `eol=lf` so local builds match Vercel — **keep that line**. If the check
ever fails again, confirm you actually changed the script before touching `vercel.json`.

### Caching headers
`apps/admin/vercel.json`: HTML `no-cache`, `/assets/*` immutable. Without the HTML rule a hashed chunk
404s into the SPA fallback → "Failed to load module script MIME text/html" after every deploy.

## Customer Portal

Customers log in at **`/portal/login`**. Two independent Supabase auth clients: `supabase` (admin,
default storage key) and `portalSupabase` (`storageKey: 'sb-portal-auth-token'`). `PortalAuthProvider`

### Passwordless login (email OTP)
Two-step: email → branded 8-digit code (Resend) → enter it. The public edge fn **`portal-request-code`**
(verify_jwt off) auto-provisions the account on first verified code, gated to active customers.
- **Enumeration-safe**: constant-time generic 200 + `EdgeRuntime.waitUntil` background provision/send.
- **`portal_login_resolve`** (00083) resolves the customer atomically and injection-safely (auth.users

  `customers.email` still logs in).
- **Rate limit** (00082/00083): `portal_login_can_send` (per-email) up front;
  `portal_login_consume_global` (whole-endpoint daily cap) consumed **only on a real send**, so probes

- **INSERT-only** on `customer_accounts` — never re-activates a revoked account (revocation stays
  owner-only in `manage-portal-account`).
- Client uses `verifyOtp({type:'email'})`; the session defaults to `sessionStorage` unless "remember me".
- 🚨 **The owner must keep public email signups disabled** (Supabase Auth → Providers → Email), or the

### Management (owner-only) — `pages/PortalManagement.tsx` at `/settings/portal`
Lists every customer with portal status / email / last login. Per row: enable, manage (disable /

### Edge fn `manage-portal-account` — do not weaken
Single function dispatching on `action` (create / relink / invite_link / reset_link / set_password /
update_email / delete). **Safety invariant:** a `classify(userId)` guard refuses to
create/relink/delete/modify any auth user whose `profiles.role` is **staff** or that belongs to a
**different** customer. Note a `handle_new_user` trigger gives **every** auth user a `profiles` row
(role defaults to `customer`), so classify checks the **role**, never mere existence.

### Security rules (keep them)
- 🚨 **Portal customers have NO direct SELECT** on `orders`/`order_items`/`documents`/`document_sends`.
  Those base tables had `USING (true)` policies, so any authenticated user could read every customer's
  data plus `cost_cents`/`internal_notes`. They now read only through the SECURITY DEFINER
  `get_portal_*` RPCs (column-whitelisted JSON, scoped to `get_portal_customer_id()` +
  `deleted_at IS NULL` + `status <> 'draft'`). **Do not re-add a broad `USING(true)` SELECT policy.**
- `customer_accounts` has **no customer UPDATE policy** (00064) — otherwise a customer could repoint
  `customer_id` (IDOR). `last_login_at` is written via the `touch_portal_last_login()` RPC scoped to
  `auth.uid()`.
- The admin app's reject-sign-outs use **`scope: 'local'`** so authenticating a non-staff account on
  the admin login never revokes that user's portal session globally.
- **Document downloads re-render from `documents.snapshot`** — PDFs are never stored
  (`documents.pdf_url` is always NULL). `getDocumentTemplate` lives in
  `components/documents/getDocumentTemplate.tsx`; `portal/utils/renderDocument.ts` lazy-imports
  `@react-pdf` to keep it out of the portal bundle. The listed amount uses `snapshot.grandTotal`, not
  the order total (credit notes were wrong).
- Reusable `components/ui/DropdownMenu.tsx` (React portal + fixed positioning) is the pattern for row
  menus that must escape `overflow-hidden`.

### Dashboard KPIs — `get_portal_stats` (00116)
Open orders + their value, outstanding / overdue amounts, YTD and lifetime spend, average order value,
last order date, next due date. `PortalHome` renders four headline tiles, a secondary figures strip and

🚨 **The `payable` CTE is a verbatim copy of `get_payment_overview_orders`'s qualifying predicate**

`total − refund_amount > 0`; overdue is `invoice_due_date < CURRENT_DATE`). That RPC builds the monthly
**Betaaloverzicht** PDF the same customer is emailed, so a divergence quotes them two different debts.

`totalSpent` is net of refunds. The recent-orders table shows **`order_date`**, the date on the

### Profile addresses answer "where do we deliver?"
`PortalAccount` renders the billing address, then the **delivery** address via
**`resolveDeliveryAddressParts`** (`utils/address.ts`), which always resolves: the shipping address when
it is filled in and flagged different, the billing one otherwise (badged *Zelfde als factuuradres*).
Same rule as `services/route.ts → resolveDeliveryAddress`, so the customer reads the address the van
drives to. It previously read the `shipping_*` columns raw, so every customer on the `true` default saw
an empty "Verzendadres" card. **Do not confuse it with `resolveShippingAddress`** in the same file,
which returns null when the addresses match because documents must not print the same block twice.

## Data Export (list pages)

The **"Exporteren"** button on list pages — separate from the document templates above.

- **`components/ui/ExportMenu.tsx`** — button + dialog: format (PDF/Excel/CSV), column ticks, row scope,
  PDF orientation. Choices persist in `localStorage` under `export:<storageKey>`.
- **`components/documents/DataExportTemplate.tsx`** — generic PDF table, `orientation` prop (landscape
  ≈786pt for wide tables), `computeTotalsRow` "Totaal" footer for `summable` columns.
- **`utils/export.ts`** — the CSV/Excel writers plus per-entity column definitions
  (`orderExportColumns`, …). Columns are `{ key, header, format?, summable?, defaultOff?, pdfWidth?,
  pdfAlign? }`; `key` may be a dotted path.

**Wiring:** pass `getAllData: () => Promise<T[]>` (the **full** filtered dataset, fetched lazily only
for the "Alle resultaten" scope), optional `pageData` / `selectedData`, plus `totalCount`, `columns`,
`filename`, `pdfTitle`, `storageKey`.

**Notes:**
- 🚨 **Column data must live on the row.** Values from a separate lookup (e.g. the Orders
  "Factuurnummer" from `fetchDocumentInfoByOrder`) must be attached to the row objects for **all**
  scopes before handing them to `ExportMenu` (see `withInvoiceNumber`). Same for unit prices —
  `withUnitPriceColumns` flattens them onto the row, **never a `format()` callback**, because
  `computeTotalsRow` reads `row[key]`.
- Adding a column to a `*ExportColumns` array automatically surfaces it as a toggle. `defaultOff` keeps
  a first-time user from getting 19 columns on portrait A4. `ExportMenu` derives its valid-key list from
  the columns it is given, so stale persisted prefs are dropped.
- `ExportMenu` supports **`variants`** (shape + its columns + its data paired, so a mismatch is
  unrepresentable) with per-variant preference keying (`export:<storageKey>:<variantKey>`), and a
  **`filterNotice`** — a filtered export is durable and forwardable, so the dialog says what is left out.
- **Price lists** export as *Per eenheid* (row per product+unit) or *Per product* (a price column per
  unit). Constants in `constants/unitTypes.ts`; **`ProductForm`'s `ALL_UNIT_TYPES` keeps its own order
  deliberately** — it picks the fallback default unit, so its order is behaviour.
- `SoldProducts.tsx` uses its own `SoldProductsTemplate`, and **Analytics → Overview** has its own
  whole-page PDF export (`utils/analyticsExport.ts`: `html-to-image` renders the DOM including Recharts
  SVG + Tailwind `oklch`, `jspdf` slices it across A4 pages) plus an Excel data sheet.

## Price lists

`pages/PriceListDetail.tsx` shows **one row per product** (not per unit). Clicking a row opens
`components/priceLists/ProductUnitsEditor.tsx` — all four unit types with editable cost + live margin,
prefilled from the **list's own** values (never product defaults, so re-saving can't clobber a custom
price/cost). A price **or** cost for a blank unit adds it; clearing **both** removes it; the row's trash
deletes the whole product. Adding goes through `PriceListProductPicker` (one row per unit, upserted on
`price_list_id,product_id,unit_type`).

🚨 `ProductGroup` carries **both `items` (all units) and `visibleItems` (filtered)`. Delete and the unit
editor must read `items`** — filtering them would delete only the visible unit while the dialog names
the whole product, or let the editor drop a hidden unit on save.

### Per-list cost-of-goods override (00068)
For bulk deals bought below the default cost.
- `price_list_items.cost_cents` is **nullable** (NULL = inherit `product_unit_prices.cost_cents` →
  `products.cost_cents`). `price_cents` is **also nullable** so a row can override cost only; a CHECK
  requires at least one.
- Flows into the immutable `order_items.cost_cents` snapshot via `OrderForm`'s price-list-aware
  `resolveLineCostCents`, so every analytics RPC reflects the negotiated cost with **no SQL change**.
- Owner-only (cost + margin columns gated by `isOwner`); labels show "aangepast" vs "standaard", the
  detail page marks overrides with an amber "inkoop" dot.
- 🚨 **`upsertPriceListItems` writes `cost_cents` per-row**, splitting the upsert into cost-managed vs
  cost-agnostic batches. This is why a price-only Excel re-import or a picker re-add never wipes a
  UI-set override. **Never collapse it into a single mixed batch** — PostgREST nulls missing keys across
  a batch.
- `scripts/wc-reconcile/sync-order-item-costs.mjs` refreshes **imported (WC) orders only** — a blanket
  refresh from current product cost clobbers negotiated in-app costs.
- Scope is price-list level; there is no per-customer cost (a different deal = a new list).

## Delivery Route (Bezorgroute)

Launched from **Sold Products** → "Route plannen": the day/range's orders become an optimized route +
truck loading order via Google Maps through a Supabase Edge Function.

### Pieces
- **`supabase/functions/plan-delivery-route/index.ts`** — the only thing that talks to Google. Verifies
  caller JWT + role, **derives candidate stops server-side** from `{delivery_date, end_date?, city?}`
  (never trusts client addresses), geocodes cache-misses only (writing lat/lng back to `customers`),
  then calls Directions. Modes `auto` (optimize) / `manual` (exact order) / `mixed` (pin+lock into
  fixed slots via greedy nearest-neighbour). >23 stops → greedy fallback + `truncatedOptimization`.
  Secret `GOOGLE_MAPS_API_KEY` — **must not be HTTP-referrer-restricted** (server-side calls send no
  referrer; use API restrictions).
- **`services/route.ts`** — `fetchRouteOrders` (one stop per customer, merged manifests),
  `planDeliveryRoute` / `computeLegsForOrder`, address resolution.
- **`hooks/useDeliveryRoute.ts`** — manual hook. Selection/locks/order/departure are local state; only
  `optimize()` / `applyManualOrder()` hit Google.
- **`components/route/*`** (`DeliveryRoutePanel`, `DeliveryStopList` with drag + up/down + a
  click-to-jump 1..N `PositionPicker`, `LoadingOrderList`) and
  **`components/documents/DeliveryRouteTemplate.tsx`** (Dutch, cyan; page 1 bezorglijst, page 2
  inlaadvolgorde; invoice-style chrome from `document_settings`, non-fatal fallback to a name-only
  header).
- **Depot** lives on the `document_settings` singleton (`depot_*`, 00055), edited in Settings → Company;
  geocoded once and cached.

### Rules
1. **Loading order = exact reverse of the delivery order**, following the **manual** order via
   `effectiveStops` — reorder a stop and the loading list + exports update instantly. No weights/volume.
2. **The manual order is authoritative and needs no Google call.** A reorder updates a derived
   `effectiveStops`/`effectiveRoute` (renumbered 1..N) immediately. `orderDirty` only blanks now-stale
   leg distances/ETAs to "—"; it does **not** block export. Re-optimize is a deliberate separate action
   that may reshuffle; "ETA's verversen" is an optional refresh.
3. 🚨 **Optimize is NOT a gate on export.** `exportReady` = every included stop has lat/lng — nothing
   more. Per-stop coords are cached on `customers` and the depot comes from `document_settings`, so
   `effectiveRoute` is **synthesised** when `route` is null and a loaded saved plan exports immediately.
   What genuinely blocks: a **never-geocoded** stop, which would silently DROP from the Maps URL (the
   amber `needsReoptimize` banner shows whenever that applies). `hasPlan` drives a "nog niet gepland"
   hint so a raw candidate list is never mistaken for an arranged round.
4. **Foreign customers auto-excluded, but the admin owns the switch** — resolved delivery country ≠ NL
   starts unticked with an amber "Buitenland" badge (export/freight, not a van delivery). Re-tickable
   per stop, and the **"Buitenland meenemen (n)"** toggle flips the whole day at once. It appears only
   when the window actually holds a foreign stop (they are the exception), defaults OFF and is
   remembered in `localStorage` (`route.includeForeign`) — a regular cross-border run is set once, not
   re-ticked every morning. The loader reads it through a **ref**, so flipping it re-seeds the
   selection without refetching the day.
5. 🚨 **Drafts are never routable.** `NON_ROUTABLE_STATUSES` (`services/route.ts`) =
   `draft`/`cancelled`/`refunded`, plus `deleted_at IS NULL`. This is **mirrored in the edge fn's
   `deriveCandidates`** — otherwise `MAX_STOPS` counts stops the client never shows. **Keep the two
   lists in sync.** The panel's status dropdown lists only statuses **present in the window** with
   counts (computed **before** the status filter, so a count never changes with the selection) and
   applies the filter **per order, before the per-customer merge**. `draft` is deliberately not an
   option.
6. **Geocode cache** on `customers` (lat/lng/geocoded_at/geocode_address_hash/geocode_status); a trigger
   nulls it when the address changes so only that row re-geocodes.
7. **Driver hand-off** — "Deel met chauffeur" opens WhatsApp with the Maps directions link; the share
   and copy text are **always Dutch**, as is the route PDF (internal/driver doc).
8. **Invoices in route order** — "Facturen (routevolgorde)" prints in the arranged sequence via the
   shared `utils/renderInvoices.tsx`. The panel emits `onRouteOrderChange(orderedIds)` so Dagafsluiting
   can offer "Sorteer op routevolgorde".
9. `google-map-api.txt` (repo root) holds the live key in plaintext — **gitignored, never commit it.**

### Saved route plans (00112)
The owner reorders stops by hand into the sequence he actually drives; that arrangement used to die
with the modal, so a manager reopening the day got the raw list and had to spend a billed optimize that
returns *Google's* order.
- **A plan is a SEQUENCE, not a snapshot** — `plan` jsonb holds ordering + selection + locks + departure
  settings plus an optional geometry cache. Manifests, addresses and order numbers are **always
  re-fetched live**, so a saved route can never hand a driver a stale product list. Do not "optimise"
  this by storing rendered stops.
- **Keyed on the DATE alone** (`route_date`,`end_date`; a single day stores `end_date = route_date` so
  the unique key is two plain columns PostgREST can name in `ON CONFLICT`) — **not** on the
  city/type/status filters, which a manager will not reproduce. Filters are stored as metadata; when
  they differ, `savedFiltersMismatch` shows a notice **instead of** the drift banner (the fingerprint
  came from a differently-filtered set, so the diff would be meaningless).
- **Drift:** `order_ids` fingerprints **every candidate order in the window**, not just the included
  ones — otherwise a deliberately excluded stop returns next time as "new". `diffRoutePlan` reports
  added/removed orders and new customers; a new customer's stop is appended **and ticked** (a missed
  delivery beats a suboptimal one). Drift sets the existing `orderDirty` flag.
- 🚨 **`get_delivery_route_plan` is an RPC purely because of `hidden_from_managers`.** A hidden order in
  the owner's fingerprint is missing from a manager's live fetch, so the diff would announce "1
  bestelling vervallen" and reveal that a hidden order exists. The RPC filters `order_ids` with the
  canonical predicate.
- **`saved_by`/`saved_at` are stamped by a BEFORE trigger**, never sent by the client (a supplied author
  is spoofable, and an upsert omitting the column would leave the previous author's name on someone
  else's re-save).
- **Both roles may save** (RLS is `is_admin_user()`): a manager who finds a real problem must be able to
  fix and re-save rather than drive a route they know is wrong; the panel naming the last saver is what
  makes that safe.
- **Dagafsluiting reads the saved plan directly** (`fetchRoutePlan`), so "Sorteer op routevolgorde" no
  longer requires opening the route panel first. A session route still wins — it is what is on screen.

## Dagafsluiting (day-close batch)

Sold Products → "Dagafsluiting": one modal producing the morning's documents for the selected
day/range.
- **`components/documents/DayCloseModal.tsx`** — the day's orders (`fetchOrders` with `dateFrom/dateTo`,
  `limit: 1000`; **draft**/cancelled/refunded filtered out — a Concept must never get an invoice number
  issued by a batch; trashed excluded by default), all selected by default. Three opt-in outputs:
  **Facturen** (one combined PDF or separate files), **Verkochte producten (PDF)**, **Bezorgroute**.
- 🚨 **`generateBatchInvoices(orderIds)` is strictly sequential** (await per order, never
  `Promise.all`) to keep invoice **order** deterministic. It reuses existing numbers via
  `fetchLatestDocumentForOrder`, so re-running a day is idempotent. (Numbering safety itself is now the
  atomic RPC's job.)
- **`utils/renderInvoices.tsx`** (`renderInvoicesToFiles`) is the shared invoice→PDF helper used by
  **both** DayCloseModal and the route panel, so ordering is identical from either entry point.
  `InvoiceTemplate.tsx` exposes `InvoicePage` (no `<Document>` wrapper) for `CombinedInvoicesTemplate`;
  `SoldProductsTemplate.tsx` exposes `buildSoldProductsDocument` for the same reason.
- 🚨 **Route exclusions carry into the batch.** A stop taken off the round in the route panel arrives
  here **unticked** (`DeliveryRoutePanel.onExcludedOrdersChange` → `SoldProducts` → `excludedOrderIds`),
  with a cyan notice naming the count — planning and closing are one flow, and silently invoicing what
  was just excluded is the error this prevents. **Only DELIBERATE exclusions propagate:**
  `useDeliveryRoute` keeps `userExcludedIds` separate from `excludedStops`, because a foreign stop is
  unticked by a **default policy** nobody chose and still needs its invoice. Flipping "Buitenland
  meenemen" is a policy change, not a per-order decision, so switching it OFF must never write into
  `userExcludedIds`. **Do not simplify this to "everything in excludedStops".**
- **Route hand-off:** the route costs a billed Google optimize, so ticking "Bezorgroute" only opens
  `DeliveryRoutePanel` — it never runs silently.
- **Separate-files caveat:** browsers throttle rapid downloads (spaced ~400ms); the combined PDF is the
  reliable default for big days. Available to owner **and** shop_manager (invoices carry no cost).

## Customer type — Horeca / Supermarkt / Overig

Admin-only classification. A **different axis** than `price_list_id` (a pricing tier), and unrelated to
the dead product `categories` table.

- **`customers.customer_type TEXT`** nullable with `CHECK (customer_type IN ('horeca','supermarkt','other'))`.
  **NULL = untagged**; existing customers were not backfilled by the migration. Text + CHECK rather than
  a Postgres enum so a 4th value is a trivial constraint swap. One type per customer; ambiguous → `other`.
- **Labels are literal, non-i18n** (identical in every language): **Horeca / Supermarkt / Overig**.
  Single source `src/constants/customerType.ts`; badge `components/ui/CustomerTypeBadge.tsx` renders
  **null when untagged** (list cells show an em-dash).
- 🚨 **NEVER on customer-facing surfaces** — no PDF template, no `get_portal_*`, no `SendDocumentModal`.
  `buildInvoiceData`'s snapshot uses an explicit field whitelist (**no object spread**), so the field on
  the orders embed cannot leak into a snapshot. Shop Manager does see it in admin lists/exports —
  "admin-only" means not customer-facing, and the label carries no cost/profit.
- **Filters:** Customers (filter + column + sort), Orders, Analytics (a "Type" dimension threaded as
  `p_customer_type`), Exports ("Klanttype"), Sold Products (**multi-select**, since a day's run is
  normally Horeca *and* Supermarkt), Route and Day Close.
- 🚨 **`customerType` is `string[]` all the way down** (`DeliveryRoutePanel` → `useDeliveryRoute` →
  `fetchRouteOrders` → `DayCloseModal`). Array props feed effect deps, so hooks key on a **joined
  primitive** (`typesKey`, mirroring `citiesKey`).
- 🚨 **Orders filters via a PostgREST inner-embed** (`customers!customer_id!inner` +
  `.eq('customer.customer_type', …)`) in **both** `fetchOrders` and `fetchOrderCount` (same
  alias/predicate or list and pagination diverge). Deliberately **not** the `buildSearchOr` id-IN-list
  path — that caps at 300 ids and a type can exceed that, silently dropping orders.

## Audit log

- `log_audit_event()` (00084) is shared by every `audit_<table>` trigger: entity type from
  `TG_TABLE_NAME`, id from `NEW.id`/`OLD.id`, full-row JSONB snapshots, actor via profiles →
  auth.users → `'system'` (a null `auth.uid()`).
- **A no-op write logs nothing** — the trigger skips updates touching only `noise_keys`, which includes
  `updated_at` (the column each table's own BEFORE UPDATE trigger bumps). So an idempotent re-import
  produces **zero** rows.
- **Pricing tables are audited** (00108): `price_list_items`, `price_lists`, `product_unit_prices` —
  all three, because a price incident spans a catalog cost change *and* price-list writes. Volume is
  accepted, not mitigated: a PostgREST upsert fires per row, so a full Excel re-import is hundreds of
  rows — which is exactly the change that needs a record.
- `search_audit_logs` / `get_audit_actors` need no change for a new type (`p_entity_type` is free text);
  add it to `AUDIT_ENTITY_TYPES` + `ENTITY_META`, and to `deriveEntityTitle` if it should resolve names.
- Titles are derived (`utils/audit.ts`), keyset-paginated, INSERT-locked and SELECT-gated to
  `is_owner()`.

## Performance

Routes are `React.lazy` and heavy libraries (`@react-pdf`, `exceljs`, `jspdf`, `html-to-image`) are
**dynamic-imported only** — this took the entry chunk from ~1.5 MB to ~125 KB gzip. **Do not revert to
static imports.** List pages paginate server-side.
